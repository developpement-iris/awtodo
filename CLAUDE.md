## Vue d'ensemble du projet

**Awtodo** est une webapp interne d'entreprise de gestion de projets (collaboratifs ou individuels), incluant gestion de tâches priorisées, gestion d'incidents, planification, et statistiques.

**Positionnement produit important :** Awtodo n'est PAS un clone de Trello/Jira/Asana. L'objectif est un outil d'organisation et de gestion personnalisable, taillé pour des besoins internes spécifiques, pas un outil générique pour chefs de projet certifiés. En cas de doute sur une fonctionnalité, privilégier la simplicité et la flexibilité (champs/statuts configurables) plutôt que la complétude façon outil pro de gestion de projet.

**Contexte d'usage :** application interne d'entreprise, pas de grand public. Authentification via SSO Microsoft obligatoire. L'API doit rester totalement ouverte car connectée à un outil de ticketing externe et à des automatisations (Power Automate notamment).

## Stack technique

- **Backend :** Django + Django REST Framework (DRF)
- **Frontend :** React (choisi pour l'écosystème de composants Kanban/Gantt/drag-and-drop et la maturité de `@azure/msal-react` pour le SSO)
- **Base de données :** PostgreSQL (via AWS RDS en prod) — ⚠️ direction actée, implémentation NON autorisée pour l'instant, voir encadré ci-dessous
- **Tâches async / événementiel :** Celery + Redis (broker Redis via ElastiCache en prod). **Câblé (session du 2026-09-22, synchronisation Outlook)** : `config/celery.py` + réglages dans `config/settings/base.py` — mais sans broker Redis provisionné pour l'instant, `CELERY_TASK_ALWAYS_EAGER=True` par défaut (tâche exécutée immédiatement, même processus, pas de vrai découplage async tant que Redis n'est pas là). Bascule vers un vrai broker : repasser ce réglage à `False`, renseigner `CELERY_BROKER_URL`, lancer un worker (`celery -A config worker`) — aucun changement de code métier.
- **Auth :** SSO Microsoft via Azure AD / Entra ID, protocole OIDC (pas SAML) — cible finale, toujours différée (tenant Azure AD réel requis)
  - Backend : `mozilla-django-oidc` ou `django-allauth` (provider Microsoft) — à trancher lors de l'implémentation du SSO
  - API : JWT via `djangorestframework-simplejwt` — **câblé (session du 2026-08-06)**, mais pour une authentification par mot de passe indépendante du SSO (login + activation de compte via invitation, voir `docs/organisation-et-comptes.md` > "Authentification par mot de passe"), pas encore pour des service accounts/clés API machine-to-machine dédiés (ticketing, Power Automate) — ce découpage-là reste à faire
  - `django-allauth` reste une dépendance déclarée mais non câblée, réservée au futur chantier SSO (provider Microsoft), pas utilisée pour le login par mot de passe actuel
  - **Exception actée (session du 2026-09-03) à « la connexion est la porte d'entrée obligatoire du site » (`App.tsx`)** : les pages de *documentation de projet publiées* sont lisibles sans compte, via une URL `/docs/<token>` (token non devinable, révocable, porté par `DocSpace.public_token` ; endpoint `GET /api/v1/docs/public/<token>/` en `AllowAny`). Seul le contenu **publié** (pages + fiches) est exposé — jamais les données de gestion (tâches, membres, budget, incidents bruts). C'est le **seul** contournement autorisé de ce garde-fou. Voir `docs/modeles-et-api.md` > "Documentation de projet".
- **Déploiement :** AWS (App Runner ou Elastic Beanstalk — pas d'EC2 nu, pas de Kubernetes/EKS à ce stade) — ⚠️ direction actée, implémentation NON autorisée pour l'instant, voir encadré ci-dessous
- **Documentation API :** `drf-spectacular` (OpenAPI/Swagger) — obligatoire pour que les équipes tierces (ticketing, Power Automate) puissent consommer l'API de façon autonome
- **Récurrence calendrier :** `python-dateutil` (`dateutil.rrule`) — moteur RRULE iCal pour le module Planning (session du 2026-09-09), backend uniquement. Le frontend construit/décrit les RRULE à la main (sous-ensemble courant), pas de lib JS ajoutée.

## Règle d'architecture transverse — AUCUNE suppression physique en base

**Règle absolue, applicable à toutes les entités du système (tâches, incidents, projets, etc.) :** aucune donnée n'est jamais supprimée physiquement de la base de données. Tout objet suit un cycle de vie qui se termine par un statut terminal (`archivée`, `rejetée`, etc.), jamais par un `DELETE`.

Conséquences pour l'implémentation :
- Tous les modèles métier utilisent un pattern de **soft-delete / statut terminal**, pas de suppression Django ORM (`.delete()`) sur ces entités.
- Prévoir un champ de statut (ou équivalent) sur chaque modèle métier permettant de distinguer les objets actifs des objets archivés/rejetés, avec un manager Django par défaut qui filtre les objets actifs (`Task.objects.active()` par exemple), pour ne pas polluer les vues courantes avec l'historique.
- Cette règle a un impact direct sur le modèle de données (voir section Modèles) et doit être respectée dans le design de chaque nouvelle app.

**⚠️ Piège Django à connaître (trouvé et corrigé le 2026-08-04) :** `StatusLifecycleModel` (dans `apps/common/models.py`) définit `objects`/`all_objects`, mais avec plusieurs bases abstraites (`UUIDModel, TimeStampedModel, StatusLifecycleModel`), Django n'hérite le `Meta` que de la **première** base qui en déclare un (`UUIDModel`, qui n'a que `abstract=True`) — le reste, y compris tout réglage de manager sur `StatusLifecycleModel.Meta`, est silencieusement ignoré. **Chaque modèle concret héritant de `StatusLifecycleModel` doit donc déclarer explicitement dans son propre `Meta`** :
```python
class Meta:
    default_manager_name = "all_objects"  # sinon les relations inverses (project.tasks.all()) masquent les objets archivés/rejetés
    base_manager_name = "all_objects"     # sinon le collecteur de suppression en cascade (on_delete=PROTECT) ne voit pas les lignes historiques
```
Déjà fait sur `Task`, `Incident`, `Project`, `ProjectMembership`, `Team`. **À reporter sur tout nouveau modèle basé sur `StatusLifecycleModel`** — sans ça, la règle "aucune suppression physique" ci-dessus est violée en pratique dès qu'on traverse une relation inverse. Régression couverte par `apps/common/tests/test_models.py`.

### Règle de dépendances entre apps

Une app "basse" dans la hiérarchie ci-dessus ne doit **jamais** importer une app "haute". Si une app a besoin de réagir à un événement d'une autre app sans lien de dépendance direct autorisé, passer par les **Django signals**, pas par un import direct. Si ce besoin se présente souvent entre deux apps précises, c'est un signal que la frontière entre ces apps est peut-être mal placée — en discuter avant de forcer un import.

### Structure interne d'une app métier type

```
apps/<nom_app>/
├── models.py
├── serializers.py       # ou serializers/ si le fichier grossit trop (un fichier par cas d'usage)
├── views.py              # ViewSets DRF
├── permissions.py        # permissions custom spécifiques à l'app
├── filters.py             # django-filter pour l'API (filtrage par statut, assigné, etc.)
├── signals.py             # émis sur create/update, consommés par notifications/integrations
├── services.py            # logique métier — voir règle ci-dessous
├── urls.py
├── admin.py
└── tests/
```

## Règles d'architecture à respecter impérativement

1. **Toute logique métier non triviale va dans `services.py`, jamais dans les serializers ou les vues.** Exemple typique : la fonction qui gère la transition de statut d'une tâche (validation par un chef de projet, passage à `disponible`/`assignée`) doit être une fonction de service testable indépendamment de la couche HTTP, notamment parce que ces transitions ont des règles métier précises (voir section Tâches).

2. **Aucun appel synchrone vers un système externe (ticketing, Power Automate, etc.) dans le flux de requête HTTP.** Toute intégration externe passe par : signal Django → tâche Celery async.

3. **Permissions par objet, pas seulement par type d'objet**, et **rôles multiples possibles sur un même projet**. Un projet collaboratif peut avoir plusieurs chefs de projet simultanément — le rôle est porté par la relation `ProjectMembership` (utilisateur × projet × rôle), jamais par un champ unique `owner` sur `Project`. Permissions DRF custom qui vérifient l'appartenance et le rôle projet par projet.

4. **PK en UUID, pas en auto-increment**, sur tous les modèles exposés via l'API (via une classe abstraite `UUIDModel` dans `apps/common`).

5. **Statuts et champs personnalisables, pas figés en dur** quand c'est pertinent. Le type de tâche (`CORRECTION`/`AJOUT`/`ÉVOLUTION`) et la priorité peuvent rester en `choices` Django au démarrage (v1), mais garder en tête une possible évolution vers un modèle configurable si le besoin de personnalisation par projet se confirme.

6. **Versionning d'API dès le départ** (`/api/v1/...`).

7. **Toute app métier a ses tests dans un dossier `tests/` dédié**.

8. **Lire un fichier avant de le modifier ; grep les appelants avant de modifier une fonction.** Rentabilise l'exploration en amont plutôt que d'éditer à l'aveugle puis corriger par itérations.

- **claude-mem** (thedotmack) — mémoire persistante entre sessions Claude Code : capture le contexte des sessions précédentes et le réinjecte automatiquement. Utile pour garder le fil sur un projet aussi long qu'Awtodo sans tout redécrire à chaque session.
- **impeccable** (pbakaus) — skill de design front, à activer pour tout travail sur les composants React/UI (évite le rendu générique "AI slop" : gradients par défaut, cards imbriquées, typographie Inter par défaut, etc.). Complète le skill `frontend-design` déjà disponible nativement.
- **task-observer** (rebelytics) — meta-skill d'observation : journalise les frictions, corrections répétées et patterns de travail pour proposer des améliorations de skills a posteriori. Ne modifie rien automatiquement, produit un log à revoir.
- **find-skills** (vercel-labs) — skill de découverte : recherche dans l'écosystème ouvert de skills agent (via `npx skills find`) si un besoin exprimé pourrait être couvert par un skill existant plutôt que réinventé à la main. Vérifie la fiabilité des skills trouvés (nombre d'installs, réputation du dépôt) avant de recommander. À utiliser quand une tâche demandée touche un domaine non couvert par les skills déjà installés, avant de proposer d'écrire du code custom.
- **headroom** (chopratejas) — proxy local de compression de contexte (logs, sorties d'outils, fichiers) avant envoi au modèle, réversible. Nécessite un processus à part tournant en continu (`headroom proxy`), pas un skill passif comme les autres — vérifier qu'il tourne avant de compter dessus.
- **graphify** (Graphify-Labs) — construit un graphe de connaissance du code (AST via tree-sitter) pour naviguer le projet sans grep aveugle. Ne se rafraîchit pas automatiquement : relancer `/graphify update` après des modifications significatives, sinon l'index devient périmé.
- **codeburn** (AgentSeal) — tableau de bord local d'usage/coût par session (aucun appel LLM, lecture des transcripts locaux). Sert aussi d'outil de vérification pour les autres skills de cette liste (voir plus bas).
- **ponytail** (DietrichGebert) — pousse vers la solution la plus simple avant d'écrire du code (stdlib/natif avant dépendance, une ligne avant un composant). Gain réel mais mesuré plus modeste que la promesse marketing (~−15% de code en benchmark indépendant, pas −54%) — à garder en tête, pas un miracle.

**Priorité en cas de conflit entre skills :** en cas de recommandation contradictoire (ex. impeccable vs frontend-design sur un choix de design), privilégier les règles explicites de ce fichier CLAUDE.md en premier, puis demander confirmation avant de trancher.

**Installation de nouveaux skills :** si `find-skills` recommande l'installation d'un nouveau skill, demander confirmation avant de l'installer, et ajouter une entrée dans cette section une fois fait.

**Vérification d'usage réel :** un skill installé ne se déclenche que si la tâche en cours le justifie — l'absence de déclenchement sur une session donnée n'est pas forcément un dysfonctionnement (ex. `ui-ux-pro-max` ne s'active pas sur un prompt purement backend, c'est attendu).
