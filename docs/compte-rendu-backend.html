Watodo — Compte-rendu backend

État au 3 août 2026 — 2 passes de développement (squelette + API en lecture seule)

1. Stack et structure posées

Django 5.2 LTS + Django REST Framework, PostgreSQL en cible production (SQLite en dev), Celery/Redis en dépendance (pas encore câblés fonctionnellement). Environnement Python 3.14 dans un .venv dédié.

Architecture en apps Django respectant la hiérarchie de dépendances définie dans CLAUDE.md : common → accounts → projects → tasks / incidents → budgeting → integrations / notifications (une app "basse" n'importe jamais une app "haute").

AppContenu
commonUUIDModel, TimeStampedModel, StatusLifecycleModel (pattern manager actif / historique), choices.py (priorités partagées)
accountsTeam, User (modèle custom, PK UUID, champ azure_oid pour le futur SSO)
projectsProject, ProjectMembership (rôles multiples par projet, contrainte d'unicité sur rôle actif)
tasksTask (cycle de statut complet, motif de rejet)
incidentsIncident (entité séparée de Task, cycle de statut propre)
budgetingBudgetEntry (schéma seul, pas de logique — hors périmètre v1)
integrations, notificationsSquelette vide, prêt à recevoir du code

Settings éclatés en base / dev / staging / production, entièrement pilotés par variables d'environnement (django-environ) — aucune valeur AWS/RDS en dur dans le code.

2. Règles transverses respectées

  • Aucune suppression physique : chaque modèle métier a un manager objects filtré sur les statuts actifs, et all_objects pour accéder à l'historique complet.
  • PK UUID partout, pas d'auto-increment.
  • Sécurité (section dédiée dans CLAUDE.md) : pas de SQL brut (.raw()/.extra() interdits), aucun secret en dur (vérifié), rate limiting DRF actif par défaut (20/min anonyme, 100/min authentifié).

3. API (passe 2)

Endpoints en lecture seule exposés sous /api/v1/ :

EndpointFiltrage
GET /api/v1/projects/—
GET /api/v1/tasks/?project=<id>par projet
GET /api/v1/incidents/?project=<id>par projet

Serializers avec libellés français prêts à l'emploi (status_display, priority_display, etc.), Task.assignee imbriqué avec un UserSerializer minimal.

Authentification API

IsAuthenticated par défaut (sûr), assoupli en AllowAny uniquement dans config/settings/dev.py (commenté « à remplacer avant staging ») pour permettre de tester le front sans SSO câblé. CORS ouvert uniquement sur http://localhost:5173 en dev.

Hors périmètre à ce stade

  • Création / édition (CRUD complet)
  • Transitions de statut (services.py toujours un stub)
  • SSO / JWT réel
  • Apps integrations et notifications
